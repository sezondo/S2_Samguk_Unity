# 현재 구현 구조

이 문서는 Notion에 길게 두지 않는 프로그래밍 구현 구조를 보관한다.

최신 기준: 2026-05-19

## 전체 흐름

- 입력은 `PlayerInput`이 받고, 플레이어 상태 변경은 `PlayerFSMManager`가 담당한다.
- 실제 기능은 `PlayerMovement`, `PlayerMeleeAttack`, `PlayerWeaponThrow`, `PlayerHackController`, `PlayerDodge` 같은 컴포넌트가 나누어 처리한다.
- `PlayerContext`는 플레이어 핵심 참조를 모아 각 기능 컴포넌트가 공유한다.
- 플레이어 계열 컴포넌트가 같은 루트의 다른 핵심 컴포넌트를 직접 찾지 않고, `PlayerContext`에서 참조를 꺼내 쓴다.
- 추후 Enemy, NPC도 `EnemyContext`, `NPCContext`처럼 도메인별 Context로 참조를 묶는다.
- `PlayerData`는 이동, 회피, 근접 공격, 무기 투척, 해킹 튜닝값을 가진다.
- 현재 `PlayerData`에는 `Health`, `Movement`, `Weapon Throw`, `Dodge`, `Hack` 기준의 실제 사용 필드만 둔다.

## 데이터 검증 기준

- 플레이어 튜닝값은 `PlayerData`, `MeleeComboData`, `PlayerMeleeAttackData`, `HackableData`, `PlayerWeaponVisualData` 같은 데이터 에셋을 기준으로 사용한다.
- 데이터 에셋이나 필수 하위 데이터가 비어 있으면 인스펙터 fallback 값을 대신 쓰지 않는다.
- 누락 또는 무효 값은 `Debug.LogError`로 드러내고, 해당 컴포넌트를 비활성화하거나 해당 흐름 진입을 중단한다.
- `PlayerMovement`, `PlayerDodge`, `PlayerHealth`, `PlayerWeaponThrow`, `PlayerHackController`, `PlayerMeleeAttack`, `PlayerWeaponVisualFSM`은 시작 시 필요한 데이터 연결과 핵심 수치 범위를 `HasValidData()`에서 검증한다.
- 런타임에 해킹 대상이 들어와야 알 수 있는 `HackableData`는 `PlayerHackController.HasValidHackableData()`에서 별도로 검증한다.
- `PlayerWeaponVisualMotion`, `PlayerWeaponVisualPresentation`의 검 비주얼 튜닝값은 `PlayerWeaponVisualData`에서만 받으며, 컴포넌트 인스펙터 fallback 값은 사용하지 않는다.
- `PlayerWeaponVisualMotion.ApplyData()`와 `PlayerWeaponVisualPresentation.ApplyData()`는 검증하지 않고 적용만 담당한다. 데이터 검증은 `PlayerWeaponVisualFSM.HasValidData()`가 담당한다.

## 입력

- 이동: `Move`
- 조준: `Look`
- 근접 공격: `MeleeAttack`
- 무기 투척 / 회수 / 해킹 취소: `WeaponThrow`
- 회피: `Dodge`
- 해킹 진행: `Hack` / E
- 일반 상호작용 예약: `Interact` / F
- 기존 화살 선택 입력 `Previous`, `Next`는 폐기했다.

## 플레이어 FSM

현재 주요 상태는 다음 기준으로 사용한다.

- `Idle`: 기본 조작 가능 상태
- `MeleeAttack`: 근접 공격 중
- `WeaponAiming`: 투척 조준 중
- `WeaponThrowing`: 검이 날아가는 중
- `WeaponReceiving`: 검이 돌아오는 중
- `Hacking`: 해킹 대상에 검이 박힌 뒤 해킹 조작 가능한 상태
- `Dodge`: 회피 중
- `Dead`: 사망 상태

해킹 관련 전환 기준은 다음과 같다.

- 검이 해킹 대상에 박힌 사건이 발생하면 `PlayerWeaponThrow`가 이벤트를 발생시킨다.
- `PlayerHackController`는 이 이벤트를 받아 활성 해킹 세션을 등록한다.
- `WeaponReceiving` 상태에서 해킹 대상에 박힌 검이 확인되면 `Hacking` 진입을 시도한다.
- `Hacking` 중에는 이동 가능, 공격 불가, 회피 가능, 사망 가능이다.
- `Hacking -> Dodge -> Hacking` 복귀가 가능하다.
- `Dead` 진입 시 현재는 해킹 세션을 정리한다. 검 처리 정책은 추후 결정한다.

## 검 투척

### PlayerWeaponThrow

- 투척 입력, 회수 입력, 투척 무기 스폰과 회수를 담당한다.
- 해킹 대상에 박힘을 직접 처리하지 않고 `EmbeddedHackWeaponRegistered` 이벤트로 알린다.
- 검 회수 완료는 `WeaponRecovered` 이벤트로 알린다.
- `PlayerHackController`를 직접 명령하지 않도록 이벤트 기반 구조로 분리했다.

### ThrownWeapon

투척 무기의 물리 상태는 다음으로 나뉜다.

- `Outbound`: 날아가는 중
- `Embedded`: 해킹 대상에 박힌 상태
- `Returning`: 플레이어에게 돌아오는 중

충돌 처리 기준은 다음과 같다.

- `Outbound`일 때만 타격과 해킹 대상 감지를 처리한다.
- `IHackable`과 `IDamageable`을 둘 다 가진 대상은 `IHackable`을 우선한다.
- `Embedded` 상태에서는 다른 적이나 오브젝트와 접촉해도 대미지나 추가 상호작용을 하지 않는다.
- 해킹 완료 또는 취소 시 `BeginReturnFromHack()`으로 회수를 시작한다.

## 해킹 / 전자 부적 삽입

개발 중 코드 명칭은 `Hack`을 사용하고, 게임 내 정식 명칭은 추후 `전자 부적 삽입`으로 정리할 예정이다.

### 주요 타입

- `IHackable`: 해킹 가능한 대상 인터페이스
- `HackableData`: 해킹 소요 시간 등 대상별 데이터만 보관하는 `ScriptableObject`
- `PlayerHackController`: 해킹 세션과 타이머를 관리하는 플레이어 컴포넌트
- `HackableTest`: 임시 테스트용 해킹 대상 컴포넌트

### HackProgressState

- `None`: 해킹 대상 없음
- `Ready`: 검이 해킹 대상에 박혀 있고, 플레이어가 아직 E를 누르지 않은 상태
- `Progress`: E 입력 후 해킹 타이머 진행 중
- `Complete`: 해킹 완료
- `Cancel`: 해킹 취소 또는 실패

### 진행 규칙

- `Ready`에서 E 입력 시 `Progress`로 전환한다.
- `Ready` 또는 `Progress`에서 우클릭을 누르면 `Cancel`로 전환하고 검을 회수한다.
- `Progress` 중 플레이어와 검 사이 거리가 `PlayerData.hack.maxHackDistance`를 넘으면 `Cancel`로 전환한다.
- 해킹 완료 시 `Complete` 처리 후 검을 자동 회수한다.
- 회피 중에도 해킹 타이머는 계속 돈다.
- 회피 중 타이머가 완료되면 회피 종료 뒤 `Hacking`으로 돌아왔을 때 완료 처리가 반영된다.

## 도깨비 환도 비주얼

### PlayerWeaponVisualFSM

- 실제 투척 무기 상태와 플레이어 FSM 상태를 바탕으로 비주얼 상태를 결정한다.
- `EmbeddedForHack` 상태를 추가했다.
- `ActiveThrownWeapon.IsEmbeddedForHack`이 참이면 이동, 회피 상태보다 `EmbeddedForHack`을 우선한다.

### PlayerWeaponVisualMotion

- 일반 상태에서는 플레이어 주변 오프셋, 조준, 공격, 회수 모션을 처리한다.
- `EmbeddedForHack` 상태에서는 비주얼 검을 실제 `ThrownWeapon` 위치에 고정한다.
- 이 상태에서는 이동 입력이나 Dodge 연출을 따라가지 않는다.

### PlayerWeaponVisualPresentation

- 비주얼 상태별 렌더러, 그림자, Trail, 이펙트 표현을 담당한다.

## 전투 공통

- `IDamageable`: 피해를 받을 수 있는 대상 인터페이스
- `IHackable`: 해킹 가능한 대상 인터페이스
- `IAttackInfoProvider`: 공격 방향과 공격 중 여부를 외부 표현/판정 컴포넌트에 제공하는 공용 인터페이스다. 현재는 `EnemyAttack`, `PlayerMeleeAttack`이 구현한다.
- `MeleeHitbox`: Player/Enemy가 함께 쓰는 공용 근접 판정 컴포넌트다. 공격 판정을 켠 순간 이미 겹쳐 있는 대상도 맞도록 현재 Overlap을 즉시 검사한다.
- `VfxManager`: 공통 VFX 스폰 관리

## 적 기본 구조

- 현재 Enemy 계열은 Player 계열처럼 Context 기반 컴포넌트 분리 구조로 시작한다.
- `EnemyContext`: Enemy 루트의 참조 주머니 역할만 한다. `EnemyAttack` 구체 참조를 들고, 공격 방향/공격 중 여부만 필요한 컴포넌트에는 `IAttackInfoProvider`로도 제공한다.
- `EnemyData`: HP, 피격 상태 시간, 이동 속도, 탐지 거리, 공격 거리, 정지 거리, 근접 단타 공격 데이터를 가진다.
- `EnemyState`: `Idle`, `Patrol`, `Chase`, `Attack`, `Hit`, `Dead`, `Hacked`를 가진다.
- `EnemyBase`: `EnemyData`를 보관하는 공통 진입점이다. 상태 전이는 담당하지 않는다.
- `EnemyFSMManager`: Enemy 상태 전이와 이동/공격 가능 여부를 관리한다.
- `EnemyHealth`: `IDamageable`을 구현하고 체력, 피격, 사망을 담당한다. 이미 `Hit` 상태일 때 추가 피격되면 `hitTimer`를 갱신한다.
- `EnemyDetector`: 플레이어 탐지를 담당하고, 감지/공격 거리와 방향을 제공한다.
- `EnemyMovement`: `EnemyDetector`의 대상 방향을 보고 이동한다. 현재는 `Attack`, `Hit`, `Dead` 중에는 이동하지 않는다. `Hacked` 정지 정책은 아직 상세 구현하지 않는다.
- `EnemyAttack`: `EnemyData.meleeAttack` 기준으로 단타 근접 공격을 처리한다. 공격 중 이동은 불가능하다. `MeleeHitbox`는 `EnemyContext`가 아니라 인스펙터에서 직접 연결한다.
- `EnemyAnimation`: `Idle`, `Move`, `Attack`, `Dead` 기준 4방향 표시를 담당한다. 좌/우는 Side 애니메이션과 `flipX` 기준이다. 공격 방향은 `EnemyContext.AttackInfoProvider`에서 읽는다.
- `MeleeHitbox`는 Player/Enemy가 함께 쓰는 공용 근접 판정 컴포넌트로 정리했다.
- 기존 `EnemyHealthTest`, `EnemyAttackTest`, `HackableTest`는 기능 단위 테스트용 컴포넌트로 남아 있다.

### Enemy 1차 테스트 결과

- `EnemyTest` 기준으로 추적, 플레이어 근접 공격 피격, HP 감소, `Hit` 상태 진입, 적 근접 공격 흐름을 1차 확인했다.
- 공격 거리 판정은 현재 Transform 중심점 거리 기준이다. 콜라이더끼리 밀려 중심점이 `attackRange` 안에 못 들어오면 공격하지 않을 수 있으므로, 테스트 에셋에서는 `attackRange`를 여유 있게 잡는다.
- 근접 판정용 `MeleeHitbox` 콜라이더는 Trigger로 쓰는 것을 기준으로 한다.
- `EnemyAnimation`은 Animator/SpriteRenderer 연결이 필요하다. 애니메이터 연결 전에는 공격 로직은 동작해도 애니메이션 확인은 불가능하다.
- `SwordRenderer`의 Missing Script 로그는 무기 렌더러 쪽 오래된 컴포넌트 참조 문제로 보이며, Enemy 공격 판정과는 별도로 정리한다.

## 말풍선 대사 시스템

1차 대사 시스템은 분기, 선택지, 다국어, 세이브 연동 없이 대사 시퀀스를 말풍선으로 표시하는 전역 시스템이다.
현재 진행 단위는 한 줄이 아니라 `DialogueStepData`이며, 한 스텝 안의 여러 대사를 동시에 말풍선으로 표시할 수 있다.

### 데이터

- `DialogueLineData`: 한 개 말풍선에 들어갈 발화자 태그, 텍스트, 글자 색/폰트 크기 override, 타자기식 출력 여부와 초당 글자 수를 가진다.
- `DialogueStepData`: 한 번에 같이 표시할 `DialogueLineData[]`와 스텝 진행 조건 `advanceByInput`, `advanceByTime`, `autoAdvanceTime`을 가진다.
- `DialogueSequenceData`: 여러 `DialogueStepData`를 순서대로 들고 있는 `ScriptableObject`다.
- `DialogueSequenceData.canPlayerMoveDuringDialogue`는 컷신형 대사에서 이동만 허용할지 정한다.
- `DialogueSequenceData.canPlayerControlDuringDialogue`는 전투 중 대사처럼 이동, 조준, 근접 공격, 무기 투척, 회피를 모두 허용할지 정한다.
- 대사 데이터에는 실제 씬 Transform을 직접 넣지 않고, `speakerTag`만 둔다.

### 실행

- `DialogueManager`: 전역 싱글톤 대사 매니저다. 현재 1차 정책은 한 번에 하나의 `DialoguePlaybackSession`만 허용한다.
- `DialogueManager`는 현재 스텝의 여러 줄을 `DialogueBubblePresenter`에 넘겨 동시에 표시한다.
- `DialoguePlaybackContext`: `sessionId`, `DialogueSequenceData`, 대사를 시작한 `DialogueEventTrigger`를 담아 전역 이벤트로 전달한다.
- `DialogueEventTrigger`: 바닥, 문, NPC, 이벤트존 같은 이벤트 오브젝트에 붙어 대사를 시작한다.
- `DialogueStartMode.Interact`: 플레이어가 근접한 상태에서 `Interact(F)`를 누르면 대사를 시작한다.
- `DialogueStartMode.Touch`: 플레이어와 접촉하면 대사를 시작한다.
- `DialogueEventTrigger.allowRepeat`는 접촉/상호작용할 때마다 반복 재생할지, 최초 1회만 재생할지 정한다.
- 이미 대사가 재생 중이면 새 재생 요청은 거부한다. 내부는 `DialoguePlaybackSession` 기준으로 둬 추후 동시 재생 확장을 고려한다.

### 말풍선 표시

- `DialogueSpeaker`: 실제 발화자 오브젝트에 붙는다. 자체 `speakerTag`와 말풍선 기준 `speechBubbleAnchor`만 가진다.
- `DialogueEventTrigger`는 해당 대사에서 사용할 `DialogueSpeaker[]` 후보를 인스펙터로 가진다.
- `DialogueBubblePresenter`는 현재 스텝의 각 `speakerTag`를 후보 `DialogueSpeaker[]` 안에서만 찾는다. 전역 `GameObject.FindGameObjectWithTag`나 Unity Tag는 사용하지 않는다.
- 발화자를 찾지 못하면 오류 로그를 띄우고 해당 대사 세션을 중단한다. fallback 발화자는 두지 않는다.
- `DialogueBubblePresenter`는 `SpeechBubbleView` 프리팹을 풀에서 꺼내 현재 스텝의 발화자 수만큼 표시하고, 다음 스텝으로 넘어가면 기존 말풍선을 숨겨 풀에 돌려놓는다.
- `SpeechBubbleView`는 말풍선 UI 하나의 표시, 숨김, 발화자 Anchor 추적, 글자별 출력 연출을 담당한다.
- 말풍선 배경은 Unity UI `Image.Type = Sliced`와 Sprite Border를 쓰는 9-slice 기준이다.
- `SpeechBubbleView`는 말풍선 조각을 직접 배치하지 않고, `bubbleImage`의 가로 크기만 조정한다.
- 말풍선 텍스트는 줄바꿈하지 않으며, 대사 줄 길이는 데이터 작성 단계에서 관리한다.
- 말풍선 가로 크기는 전체 문장 기준 `TMP_Text.preferredWidth`와 `horizontalOffset`을 사용하고, Text와 말풍선 본체의 가로 스케일 차이를 보정해 계산한다.
- 말풍선 높이와 꼬리 크기/위치는 코드에서 조정하지 않고 프리팹 RectTransform 값을 사용한다.
- 말풍선 위치는 `speakerAnchor`의 월드 좌표를 화면/UI 좌표로 변환해 따라간다.
- 한글 텍스트는 `Assets/Resources/Fonts/NotoSansKR-VF.ttf`를 런타임에 로드해 Dynamic TMP Font Asset으로 적용한다.
- 말풍선 크기는 전체 문장 기준으로 먼저 계산하고, 타자기식 출력은 TMP `maxVisibleCharacters`로 표시 글자 수만 늘린다.
- 글자 출력 중 `Interact(F)` 입력을 누르면 현재 스텝의 모든 말풍선을 즉시 완성한다.
- 자동 진행 타이머는 현재 스텝의 모든 말풍선 글자 출력이 완료된 뒤부터 카운트한다.

### 조작 잠금

- `DialogueManager`는 대사 시작/줄 변경/종료를 전역 이벤트로 발행한다.
- `PlayerControlLock`은 전역 대사 이벤트를 구독해 `Dialogue` 사유의 이동, 조준, 근접 공격, 무기 투척, 회피 잠금을 걸거나 푼다.
- `PlayerControlLock`은 대사 중 조준/방향 갱신을 막기 위한 `Look` 잠금도 관리한다.
- `PlayerInput`은 원시 입력은 계속 읽되, `PlayerControlLock` 상태에 따라 이동, 조준, 근접 공격, 무기 투척, 회피 입력 공개값을 필터링한다.
- 대사 진행용 `Interact` 입력은 잠금으로 필터링하지 않는다.
- `DialogueSequenceData.canPlayerControlDuringDialogue`가 켜져 있으면 대사 중 이동, 조준, 근접 공격, 무기 투척, 회피를 모두 허용한다.
- `canPlayerControlDuringDialogue`가 꺼져 있고 `canPlayerMoveDuringDialogue`가 켜져 있으면 이동만 허용하고 조준, 근접 공격, 무기 투척, 회피는 잠근다.
- 두 값이 모두 꺼져 있으면 컷신형 대사로 보고 이동, 조준, 근접 공격, 무기 투척, 회피를 모두 잠근다.
- `PlayerFSMManager`는 `PlayerControlLock`을 보고 `CanMove`, `CanEnterMeleeAttack`, `CanEnterWeaponAiming`, `CanEnterDodge` 판단에 반영한다.
- 기능 컴포넌트는 각자 잠금 컴포넌트를 직접 보지 않고, 기존처럼 `PlayerFSMManager.RequestState` 또는 `PlayerFSMManager.CanMove`를 통해 최종 허용 여부를 확인한다.

## 레거시 정리 상태

- 기존 화살 선택 입력은 폐기했다.
- `PlayerInput`은 이제 `WeaponThrow` 액션만 무기 투척 입력으로 사용하며, 레거시 `Bow` 액션 fallback은 제거했다.
- `PlayerLoadout`에서는 화살 테이블, 보유 화살, 장착 화살 API를 제거하고 플레이어 데이터와 근접 콤보 데이터만 보관한다.
- `PlayerContext`에서는 `PlayerArrowSwitcher` 참조를 제거해 플레이어 런타임 의존성을 끊었다.
- `PlayerArrowSwitcher`는 기존 씬/프리팹 참조 호환을 위해 빈 컴포넌트로 남기고 비활성화한다.
- `PlayerArrowSwitcher`, `PlayerBow`, `Arrow`, `ArrowData`, `ArrowDataTable`은 `Assets/Script/Legacy`에 모아둔 고립된 레거시 코드다.
- 활/화살 레거시는 당장 삭제하지 않고, 씬/프리팹 정리 후 완전 삭제 여부를 판단한다.
- Notion에는 폐기 구조를 길게 보관하지 않고, 필요한 세부 내용은 이 문서와 작업일지에 남긴다.
- 앞으로 Notion 페이지에 프로그램 구현 내용을 반영할 때는 이 문서의 현재 구현 구조도 함께 업데이트한다.

## 추후 검토 사항

- `PlayerWeaponThrow`와 `PlayerHackController`의 이벤트 경계가 장기적으로 적절한지 검토한다.
- 사망 시 박힌 검을 즉시 소멸시킬지, 회수시킬지, 현장에 남길지 결정한다.
- 해킹 연결선 연출을 추가할 때 거리 단계별 색상 기준을 정한다.
- 게임 내 명칭 `전자 부적 삽입`을 UI/대사/튜토리얼에 어떻게 녹일지 정한다.
- 말풍선 대사의 선택지, 분기, 세이브 연동은 튜토리얼 맵 이후 필요 범위를 다시 정한다.
- `EnemyState.Hit`는 나중에 단순 피격 상태를 넘어 경직도 개념으로 확장할 수 있다.
- `EnemyState.Hacked`는 지금 상세 구현하지 않는다. 추후 정지, 아군화, 자폭 같은 하위 상태나 정책으로 확장할 수 있다.
- 해킹 이후 피아식별은 플레이어 vs 적 2진영만 전제하지 않는다. 플레이어 측 아군, 해킹으로 아군화된 적, 제3 세력까지 고려한다. 참고 방향은 XCOM 2의 XCOM / Lost / Alien처럼 다자 전투가 가능한 구조다.
- `EnemyDetector`는 현재 1차 구현으로 플레이어 방향과 거리만 단순 제공한다. 테스트를 먼저 진행한 뒤, 다자 피아식별, 대상 선택 우선순위, 길찾기와 함께 확장 여부를 결정한다.
- 적 시야 판정은 패트롤 구현 시 함께 검토한다. 예를 들어 벽 뒤의 플레이어는 감지하지 못하는 방식이 필요할 수 있다.
- `EnemyAttack`은 현재 근접 단타 공격이다. 후순위로 공격 시작 시 플레이어와 가장 가까운 8방향 중 하나를 고정해 판정하는 방식을 검토한다.
- `MeleeHitbox`는 공용 카테고리 컴포넌트이므로 Enemy 전용 Context 참조로 묶지 않고, 필요한 공격 컴포넌트가 인스펙터에서 직접 받는 방향으로 둔다.
- `MeleeHitbox`의 타겟 레이어 필터는 현재 인스펙터 값으로 판정하지만, 추후 `Activate()` 호출 시 공격 주체나 진영에 맞춰 타겟 필터를 넘기는 구조로 바꿀 수 있다.
- `MeleeHitbox.CanHitTarget()`의 `targetLayers` 비트마스크 판정은 현재 테스트용으로 유지한다. 다자 피아식별이 들어오면 레이어만으로는 부족할 수 있으므로 수정한다.
- `EnemyHealth`의 Hit 상태에는 나중에 Hit 애니메이션을 연결한다.
